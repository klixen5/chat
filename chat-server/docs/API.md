# Chat API · v1

## Адреса и модель работы

```text
HTTP:      http://127.0.0.1:3001
WebSocket: ws://127.0.0.1:3001/ws
```

Можно использовать `localhost` вместо `127.0.0.1`. Порт меняется через `PORT`.

REST нужен для комнат и истории. WebSocket — для входа под именем, выбора комнаты и обмена новыми сообщениями. Авторизация, cookie и токены не нужны. В каждый момент одно WebSocket-соединение находится максимум в одной комнате.

Даты — строки ISO 8601 в UTC. `id` сообщения — положительное целое число, возрастающее при сохранении. Пропуски в числах допустимы. Отображай сообщения по `id`, время форматируй на клиенте.

## Модели

### Комната

```json
{
  "id": "react",
  "name": "React",
  "description": "Компоненты, хуки и разработка приложений."
}
```

Готовые идентификаторы: `javascript`, `react`, `algorithms`. Создание комнат пока не предусмотрено.

### Сообщение

```json
{
  "id": 42,
  "roomId": "react",
  "clientMessageId": "5c7eaf01-5fd0-430d-841c-2551ed41a496",
  "authorName": "Саша",
  "text": "Всем привет!",
  "createdAt": "2026-10-22T12:42:00.000Z"
}
```

- `id`, `authorName`, `createdAt` задаёт сервер. Присланное в `message:send` имя автора игнорируется.
- `clientMessageId` генерирует фронтенд один раз на новое сообщение: `crypto.randomUUID()`.
- Если повторяешь **то же** сообщение после обрыва, отправляй тот же `clientMessageId`, комнату, текст и используй то же имя. Тогда в базе останется одна запись.
- Для нового сообщения всегда нужен новый `clientMessageId`, даже если текст совпадает.
- Имя хранится в каждой записи. После выхода автора сообщения остаются. Отдельной таблицы пользователей нет.
- Одинаковые имена разрешены; имя не доказывает личность. Не используй его как уникальный ID пользователя.
- Текст — обычная строка. В React выводи его как текст, без `dangerouslySetInnerHTML`.

## REST

### `GET /api/health`

Проверяет доступность приложения и базы. Успех `200`:

```json
{ "status": "ok", "database": "connected" }
```

Если база недоступна — `503` с кодом `DATABASE_UNAVAILABLE`.

### `GET /api/rooms`

Список комнат. Успех `200`:

```json
{
  "items": [
    { "id": "javascript", "name": "JavaScript", "description": "Обсуждаем язык, браузер и задачи." },
    { "id": "react", "name": "React", "description": "Компоненты, хуки и разработка приложений." },
    { "id": "algorithms", "name": "Алгоритмы", "description": "Разбираем подходы к решению задач." }
  ]
}
```

### `GET /api/rooms/:roomId`

Одна комната. Успех `200`: `{ "room": { ... } }`. Неизвестная комната: `404 ROOM_NOT_FOUND`.

### `GET /api/rooms/:roomId/messages`

История комнаты. Успех `200`:

```json
{
  "items": [
    {
      "id": 42,
      "roomId": "react",
      "clientMessageId": "5c7eaf01-5fd0-430d-841c-2551ed41a496",
      "authorName": "Саша",
      "text": "Всем привет!",
      "createdAt": "2026-10-22T12:42:00.000Z"
    }
  ],
  "pagination": {
    "limit": 30,
    "hasMore": false,
    "nextBefore": 42,
    "nextAfter": 42
  }
}
```

`items` **всегда идут от старых сообщений к новым**, в том числе при загрузке предыдущих страниц.

| Параметр | Назначение |
|---|---|
| `limit` | Сколько записей загрузить: от 1 до 100; по умолчанию 30 |
| `before` | Загрузить сообщения с `id` строго меньше указанного |
| `after` | Загрузить сообщения с `id` строго больше указанного |

`before` и `after` нельзя передавать вместе. Курсор — просто ID, он не обязан существовать в выбранной комнате.

Примеры:

```text
GET /api/rooms/react/messages?limit=30
GET /api/rooms/react/messages?limit=30&before=42
GET /api/rooms/react/messages?limit=100&after=42
```

- **Без курсора:** последние `limit` сообщений. `hasMore` означает, что есть более старые.
- **С `before`:** ближайшие предыдущие `limit` сообщений. Для следующей старой страницы используй `pagination.nextBefore`; `hasMore` по-прежнему относится к старым сообщениям.
- **С `after`:** первые `limit` более новых сообщений. Это нужно для восстановления после обрыва. Если `hasMore: true`, повтори запрос с `after=pagination.nextAfter`, пока не получишь всё.
- `nextBefore` — ID первой записи ответа; `nextAfter` — последней. Это курсоры, а не гарантия наличия следующей страницы: проверяй `hasMore`.
- Если записей нет: `items: []`, `hasMore: false`, оба курсора `null`.

### Ошибки HTTP

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "limit должен быть положительным целым числом.",
    "details": { "field": "limit" }
  }
}
```

`details` необязательно. В `fetch` ответ `400` или `500` сам по себе не отклоняет промис: проверяй `response.ok`.

| HTTP | Код | Причина |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Некорректные параметры |
| 403 | `ORIGIN_NOT_ALLOWED` | Фронтенд с неразрешённого origin |
| 404 | `ROOM_NOT_FOUND` | Неизвестная комната |
| 404 | `NOT_FOUND` | Неизвестный маршрут |
| 503 | `DATABASE_UNAVAILABLE` | База недоступна при проверке `/api/health` |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка, включая сбой базы в других запросах |

Записывающих REST-маршрутов нет: отправка сообщений происходит только через WebSocket.

## WebSocket: общий формат

Во фронтенде используй **нативный браузерный `WebSocket`**, без пакета `ws` и без Socket.IO:

```js
const socket = new WebSocket('ws://127.0.0.1:3001/ws');
socket.addEventListener('message', event => {
  const packet = JSON.parse(event.data);
  console.log(packet.type, packet.data);
});
```

События отправляются как JSON-строки:

```json
{
  "type": "room:join",
  "requestId": "join-react",
  "data": { "roomId": "react" }
}
```

- `type` — название события.
- `data` — объект данных.
- `requestId` — необязательная строка длиной 1–100 символов. Сервер возвращает её в прямом ответе или ошибке, чтобы сопоставить действие и результат. Генерируй разные значения для разных запросов.
- У общих рассылок `requestId` нет. Например, `message:created` приходит всем участникам, а `message:ack` с `requestId` — только отправителю.
- Отправлять можно только после открытия соединения (`socket.readyState === WebSocket.OPEN`).

### Порядок входа

```text
Открыть WebSocket
← connection:ready
→ session:identify
← session:ready
→ room:join
← room:joined
Загрузить историю через REST; обрабатывать message:created
→ message:send
← message:created (всем в комнате, включая отправителя)
← message:ack (только отправителю)
```

Для начала реализуй именно этот сценарий. Обработчик `message` установи сразу при создании сокета.

## Клиент → сервер

### `session:identify` — задать имя

```json
{ "type": "session:identify", "requestId": "identify-1", "data": { "name": "Саша" } }
```

Имя после удаления пробелов по краям: от 2 до 30 Unicode-символов, без переносов строк и управляющих символов.

Ответ `session:ready`:

```json
{
  "type": "session:ready",
  "requestId": "identify-1",
  "data": { "connectionId": "67f60f62-2ffd-49a4-ae9a-5a77f5194cc1", "name": "Саша" }
}
```

Задать имя можно только один раз за соединение. Для смены имени закрой соединение и создай новое. При переподключении всегда заново отправляй `session:identify`.

### `room:join` — войти или переключиться

```json
{ "type": "room:join", "requestId": "join-1", "data": { "roomId": "react" } }
```

Ответ:

```json
{
  "type": "room:joined",
  "requestId": "join-1",
  "data": {
    "room": { "id": "react", "name": "React", "description": "Компоненты, хуки и разработка приложений." }
  }
}
```

Сервер автоматически выходит из предыдущей комнаты. Повторный вход в ту же комнату разрешён. При неверном `roomId` старая комната остаётся текущей. История в этом событии **не приходит**, её нужно запросить REST-запросом.

### `room:leave` — выйти из текущей комнаты

```json
{ "type": "room:leave", "requestId": "leave-1", "data": {} }
```

Ответ:

```json
{ "type": "room:left", "requestId": "leave-1", "data": { "roomId": "react" } }
```

Если комнаты не было, `roomId: null`. Соединение и имя сохраняются. Закрытие сокета также автоматически прекращает получение сообщений.

### `message:send` — отправить сообщение

```json
{
  "type": "message:send",
  "requestId": "send-1",
  "data": {
    "roomId": "react",
    "clientMessageId": "5c7eaf01-5fd0-430d-841c-2551ed41a496",
    "text": "Всем привет!"
  }
}
```

Перед этим нужно задать имя и войти в комнату. `roomId` должен совпадать с текущей комнатой: это защищает от случайной отправки черновика в другую комнату во время переключения.

Текст после удаления пробелов по краям: от 1 до 2000 Unicode-символов, переносы строк допустимы. Пустое сообщение отклоняется. `clientMessageId` обязателен, формат UUID.

Сервер сначала сохраняет запись, затем рассылает `message:created` и подтверждает отправителю через `message:ack`.

## Сервер → клиент

### `connection:ready`

Приходит сразу после подключения, до входа под именем:

```json
{ "type": "connection:ready", "data": { "connectionId": "67f60f62-2ffd-49a4-ae9a-5a77f5194cc1" } }
```

Это ID соединения, не постоянный ID пользователя. После переподключения будет другим.

### `message:created`

Приходит всем клиентам текущей комнаты, включая отправителя:

```json
{
  "type": "message:created",
  "data": {
    "message": {
      "id": 42,
      "roomId": "react",
      "clientMessageId": "5c7eaf01-5fd0-430d-841c-2551ed41a496",
      "authorName": "Саша",
      "text": "Всем привет!",
      "createdAt": "2026-10-22T12:42:00.000Z"
    }
  }
}
```

### `message:ack`

Личное подтверждение отправителю:

```json
{
  "type": "message:ack",
  "requestId": "send-1",
  "data": {
    "message": {
      "id": 42,
      "roomId": "react",
      "clientMessageId": "5c7eaf01-5fd0-430d-841c-2551ed41a496",
      "authorName": "Саша",
      "text": "Всем привет!",
      "createdAt": "2026-10-22T12:42:00.000Z"
    },
    "duplicate": false
  }
}
```

`duplicate: true` означает, что такая запись уже была сохранена; повторной рассылки `message:created` не будет. Это успешное подтверждение, не ошибка.

Для первой версии **добавляй сообщения в список через `message:created`**, а `message:ack` используй как подтверждение отправки. При повторе и восстановлении также можно объединять данные из ack со списком — с проверкой `id`. Не добавляй одну запись дважды из двух событий.

### `error`

Ошибки протокола приходят как обычное WebSocket-сообщение:

```json
{
  "type": "error",
  "requestId": "send-1",
  "data": {
    "code": "VALIDATION_ERROR",
    "message": "Поле text: допустимая длина от 1 до 2000 символов.",
    "details": { "field": "text" }
  }
}
```

Это **не** браузерное событие `socket.onerror`: читай такой пакет в обработчике `message`. `socket.onerror` и `close` отвечают за проблемы самого подключения.

| Код | Причина / действие |
|---|---|
| `INVALID_JSON` | Некорректный JSON или бинарный пакет |
| `INVALID_EVENT` | Нет строкового `type` |
| `VALIDATION_ERROR` | Неверные поля, имя, текст или UUID |
| `IDENTIFY_REQUIRED` | Сначала нужно задать имя |
| `ALREADY_IDENTIFIED` | Имя уже задано на этом соединении |
| `ROOM_NOT_FOUND` | Неизвестная комната |
| `JOIN_REQUIRED` | Сначала нужно войти в комнату |
| `ROOM_MISMATCH` | Сообщение адресовано другой комнате |
| `MESSAGE_ID_CONFLICT` | Тот же UUID использован с другим текстом, именем или комнатой |
| `UNKNOWN_EVENT` | Неподдерживаемый `type` |
| `RATE_LIMITED` | Больше 60 событий за 10 секунд на соединение; сокет закрывается |
| `INTERNAL_ERROR` | Сервер не смог обработать действие; отправку можно повторить с тем же UUID |

Обычная ошибка проверки не закрывает соединение: исправь данные и продолжай.

## История и новые сообщения: как не потерять запись

Между загрузкой истории и входом в комнату могут прийти новые сообщения. Поэтому:

1. Установи обработчики WebSocket, задай имя, отправь `room:join`.
2. После `room:joined` начни принимать `message:created` для этой комнаты и запроси историю.
3. Ответ истории **объедини** с уже полученными сообщениями по `id`; отсортируй по `id`.
4. Не заменяй весь список ответом истории без объединения: так можно стереть сообщение, пришедшее во время запроса.

При быстрой смене комнаты отменяй старый `fetch` через `AbortController` или игнорируй его результат. Проверяй `message.roomId`, чтобы запоздавший пакет предыдущей комнаты не попал в текущую.

## Обрыв и повторное подключение

Браузерный WebSocket сам не переподключается. На первом этапе можно показать кнопку «Подключиться снова»; автоматические попытки добавить позже.

После обрыва:

1. Создай новый WebSocket и снова задай имя.
2. Войди в прежнюю комнату.
3. Получи пропущенные записи через `GET .../messages?after=<последний сохранённый id>&limit=100`.
4. Если `hasMore: true`, продолжай с `after=nextAfter`. Объединяй с живыми событиями по `id`.
5. Если отправлял сообщение, но ack не пришёл, повтори отправку с исходным `clientMessageId`. Новый UUID создал бы дубликат.

Для восстановления сохраняй курсор последней успешно загруженной записи **до обрыва**, не подменяй его первым живым сообщением после переподключения до завершения догрузки. Это важно для пропусков.

Сервер отправляет служебный ping каждые 30 секунд; браузер отвечает pong автоматически. Писать heartbeat во фронтенде не требуется.

При штатной остановке сервер закрывает сокеты с кодом `1001`. Слишком большой пакет (>16 КиБ) закрывается с `1009`, превышение частоты — с `1008`, слишком медленное чтение — с `1013`. Для восстановления подключись заново. При аварийном разрыве браузер может сообщить `1006`.

## Проверка из консоли браузера

Открой страницу своего локального React-приложения. Этот пример просто проверяет сервер, это не готовый React-код:

```js
const socket = new WebSocket('ws://127.0.0.1:3001/ws');

socket.addEventListener('message', event => {
  const packet = JSON.parse(event.data);
  console.log(packet);

  if (packet.type === 'connection:ready') {
    socket.send(JSON.stringify({ type: 'session:identify', data: { name: 'Саша' } }));
  }
  if (packet.type === 'session:ready') {
    socket.send(JSON.stringify({ type: 'room:join', data: { roomId: 'react' } }));
  }
});

// После получения room:joined выполни отдельно:
socket.send(JSON.stringify({
  type: 'message:send',
  requestId: crypto.randomUUID(),
  data: { roomId: 'react', clientMessageId: crypto.randomUUID(), text: 'Привет!' }
}));

// При завершении:
socket.close();
```

Открой вторую вкладку, войди с другим именем в `react` и проверь доставку. В комнате `algorithms` эти сообщения приходить не должны.

## Подключение в React

Реализацию пишешь ты. Ориентиры по жизненному циклу:

- Сокет — внешнее соединение: создавать его в эффекте, закрывать в cleanup, удалять обработчики.
- Сам сокет можно хранить в `ref`; статус подключения, комнаты, сообщения, ошибки — в состоянии.
- В Strict Mode цикл «подключение → очистка → подключение» допустим. Не подавляй эффект флагом ради одного подключения.
- Создавай UUID сообщения в обработчике отправки, не во время рендера.
- При добавлении входящего сообщения используй актуальное предыдущее состояние, не устаревшее замыкание.
- Статус «отправлено» означает подтверждение сервером; статуса «прочитано» в API нет.

Начни с имени, одной комнаты и отправки в двух вкладках. Потом добавь выбор комнат, историю, более старые сообщения, обработку ошибок и переподключение.
